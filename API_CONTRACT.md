# Контракт REST API (черновик под FastAPI)

Клиент уже написан под этот контракт. Реализуете его на VPS — переключаете
`AppConfig.useMockBackend = false`, и приложение работает с живым сервером без правок UI.

Общие правила:

- База: `https://<домен>/v1`
- Кодировка тел: JSON, ключи в `snake_case`
- Даты: ISO-8601 с таймзоной, например `2026-09-13T18:00:00+03:00`
- Авторизация: заголовок `Authorization: Bearer <access_token>`
- Ошибки: FastAPI-формат `{"detail": "текст"}` либо `{"detail": [{"msg": "текст"}]}`
  (клиент разбирает оба варианта и показывает `detail` пользователю)

## Аутентификация

### `POST /auth/register`

```json
{ "name": "Александр", "email": "dad@example.com", "password": "secret" }
```

Ограничение: 5 попыток в час с одного IP — здесь считаются **все** запросы,
включая успешные, потому что вредна как раз массовая регистрация.
При превышении — `429`, как у входа.

### `POST /auth/login`

```json
{ "email": "dad@example.com", "password": "secret" }
```

Эндпоинт ограничен по числу **неудачных** попыток: 5 за 15 минут на аккаунт
и 20 за 5 минут на IP-адрес. При превышении — `429` с заголовком `Retry-After`
(секунды) и человеческим текстом в `detail`:

```json
{ "detail": "Слишком много попыток входа. Повторите через 14 мин." }
```

Пока лимит активен, не проходит и верный пароль. Успешный вход обнуляет
счётчик аккаунта. Значения настраиваются через переменные окружения
`LOGIN_RATE_LIMIT_*`.

Ответ обоих эндпоинтов — `200`:

```json
{
  "access_token": "ey...",
  "refresh_token": "ey...",
  "expires_in": 3600,
  "user": {
    "id": "11111111-1111-1111-1111-111111111111",
    "name": "Александр",
    "email": "dad@example.com",
    "role": "parent",
    "color_hex": "#3B82F6"
  }
}
```

### `POST /auth/refresh`

```json
{ "refresh_token": "ey..." }
```

Ответ `200`:

```json
{ "access_token": "ey...", "refresh_token": "ey...", "expires_in": 3600 }
```

Важно: при невалидном refresh-токене верните `401` — клиент сам разлогинит пользователя.

### `POST /auth/logout`

Без тела. Ответ `204`. Клиент чистит Keychain независимо от результата.

### `GET /me`

Ответ `200` — объект `user` из примера выше. Используется для восстановления сессии при старте.

### `GET /family/members`

Ответ `200` — массив объектов `user`.

## Задачи

Объект задачи:

```json
{
  "id": "b3f1...",
  "title": "Забрать Соню с тренировки",
  "notes": "Секция заканчивается в 18:30",
  "due_date": "2026-09-13T18:00:00+03:00",
  "priority": "high",
  "status": "todo",
  "assignee_id": "1111...",
  "assignee_name": "Александр",
  "created_by_id": "2222...",
  "created_at": "2026-09-10T09:00:00+03:00",
  "updated_at": "2026-09-12T11:20:00+03:00"
}
```

- `priority`: `low` | `medium` | `high`
- `status`: `todo` | `in_progress` | `done`
- `visibility`: `family` | `parents`

### Видимость

`visibility` управляет доступом **на сервере**, а не подсказывает клиенту, что прятать.
Задача со значением `parents` не приходит ребёнку ни в списке, ни по прямой ссылке —
там она даёт `404`, а не `403`, чтобы не подтверждать её существование.

Правила:

- поле необязательное, по умолчанию `family` — клиент, который о нём не знает, работает как прежде;
- задать `parents` может только родитель, иначе `403`;
- задачу со значением `parents` нельзя назначить ребёнку — `422`: иначе она висела бы
  на человеке, который её не видит.

> `convertFromSnakeCase` в Swift преобразует только **ключи**, но не **значения**.
> Поэтому в `TaskStatus` raw value задан явно (`case inProgress = "in_progress"`) —
> сервер должен отдавать ровно `in_progress`, а не `inProgress`.

### `GET /tasks`

Ответ `200` — массив задач семьи текущего пользователя.

### `POST /tasks`

```json
{
  "title": "Купить продукты",
  "notes": null,
  "due_date": null,
  "priority": "medium",
  "assignee_id": "2222..."
}
```

Ответ `201` — созданная задача целиком.

### `PUT /tasks/{id}`

Полная замена (не PATCH — так нет неоднозначности «null = не менять»):

```json
{
  "title": "Купить продукты",
  "notes": "Молоко, хлеб",
  "due_date": "2026-09-14T19:00:00+03:00",
  "priority": "high",
  "status": "in_progress",
  "assignee_id": "2222..."
}
```

Ответ `200` — обновлённая задача.

### `DELETE /tasks/{id}`

Ответ `204`.

## Заметки

Заметка — это заголовок и необязательный текст. Ни сроков, ни статусов, ни исполнителей.

```json
{
  "id": "9c2a...",
  "title": "Список покупок",
  "body": "Молоко, хлеб, кофе",
  "visibility": "family",
  "author_id": "1111...",
  "author_name": "Александр",
  "created_at": "2026-09-13T09:00:00+03:00",
  "updated_at": "2026-09-13T11:20:00+03:00"
}
```

- `GET /notes` — список семьи, недавно изменённые сверху
- `POST /notes` — `{title, body?, visibility?}`, ответ `201`
- `PUT /notes/{id}` — полная замена, ответ `200`
- `DELETE /notes/{id}` — ответ `204`

`visibility` работает точно так же, как у задач. Редактировать заметку может любой,
кто её видит: это общий блокнот семьи, а не личные записи автора. `author_name`
при правках не меняется — это тот, кто её завёл.

## Коды ответов, которые обрабатывает клиент

| Код | Поведение приложения |
|-----|----------------------|
| `401` | Одна попытка refresh, затем разлогин |
| `403` | «Недостаточно прав» |
| `404` | «Данные не найдены» |
| `400/409/422` | Показывает `detail` как текст ошибки валидации |
| `429` | `APIError.tooManyRequests`: показывает `detail`, кнопки «Повторить» нет |
| `5xx` | Показывает ошибку с кнопкой «Повторить» |

Про `429`: клиент читает заголовок `Retry-After` и кладёт его в
`APIError.tooManyRequests(message:retryAfter:)`. Если сервер ответит без `detail`,
текст будет собран на клиенте из `Retry-After`. Кнопка «Повторить» намеренно
не показывается — она предлагала бы ровно то действие, которое заблокировано.

## Эталонная реализация

Контракт реализован в [backend/](backend/) на FastAPI. Тесты в
`backend/tests/test_contract.py` проверяют именно совпадение форм ответа
с ожиданиями Swift-клиента — запускайте их после любой правки схемы.

Две вещи реализация добавляет сверх контракта (клиент их не использует,
обратная совместимость не нарушена):

- необязательное поле `invite_code` в `POST /auth/register` — без него создаётся
  новая семья с ролью `parent`, с ним пользователь входит в существующую как `child`;
- `GET /family` — возвращает `{id, name, invite_code}` для будущего экрана «Пригласить».

Отдельно про даты: сервер нормализует все входящие значения к UTC и всегда отдаёт
смещение (`2026-09-13T18:00:00+03:00` вернётся как `2026-09-13T15:00:00+00:00` —
тот же момент времени). Это не косметика: `ISO8601DateFormatter` с
`.withInternetDateTime` вернёт `nil` на строке без часового пояса, и декодирование
задачи упадёт целиком.
